# Задание 4

Изменения в схеме обозначены зеленым.

#### **Требуется ли `osago-aggregator` своё хранилище данных?**

Да, `osago-aggregator`**нужен свой экземпляр БД** (`osago-aggregator-db`), потому что:

* Он должен **хранить статусы заявок** (создана, в обработке, получен ответ, истек таймаут).
* Логировать **ошибки и задержки** при взаимодействии со страховыми компаниями.
* Хранить **метаданные по процессу** (время отправки, время получения ответа, идентификаторы компаний).

**Вывод**:
Добавить на схему `osago-aggregator-db (PostgreSQL)` и соединить его с `osago-aggregator`.

#### **Какой API `osago-aggregator` предоставляет `core-app`?**

1. **REST API** (стандартный, простой, но не идеален для стриминга ответов).
2. **gRPC** (более эффективный для высоконагруженных сервисов, подходит лучше, чем REST).

Выбранный вариант:
**gRPC API** для быстрого обмена бинарными данными.

Методы API:

* `POST /osago/request` → создаёт заявку, возвращает `request_id`.
* `GET /osago/result/{request_id}` → получает список предложений.

**Вывод**:
На схеме отразить связь `gRPC` между `core-app` и `osago-aggregator`.

**Средство интеграции между `core-app` и `osago-aggregator`**

* Используем **gRPC**, потому что:
  * Он **быстрее** REST.
  * Поддерживает **асинхронные ответы**.
  * Лучше масштабируется при **высокой нагрузке**.

**Вывод**:
На схеме добавить **gRPC API** между `core-app` и `osago-aggregator`.

#### **API для веб-приложения в `core-app`**

Поскольку пользователю нужно видеть предложения **по мере их поступления**, REST **не подходит**. Вместо этого используем **WebSockets**:

* **WebSockets** позволяют **потоково отправлять предложения** в браузер по мере их поступления.
* `core-app`**сначала отправляет запрос на оформление ОСАГО через gRPC**, а затем **асинхронно отправляет результаты в браузер**.

**Вывод**:
На схему добавить **WebSockets API** между `InsureTech Web` и `core-app`.

#### **Средство интеграции между веб-приложением и `core-app`**

* `POST /osago/request` (REST) — отправка заявки.
* **WebSockets** — получение предложений в реальном времени.

**Вывод**:
На схеме добавить **WebSockets** между `InsureTech Web` и `core-app`.

### **Применение паттернов отказоустойчивости**

Для предотвращения сбоев при высокой нагрузке добавляем:

1. **Rate Limiting** (ограничение запросов)
   * Применяем к `osago-aggregator`, чтобы партнеры не перегружали сервис.
   * Применяем на API Gateway перед `core-app` (для защиты от перегрузки веб-приложением).
   * **Отразить на схеме возле API Gateway и `osago-aggregator`**.
2. **Circuit Breaker** (предотвращение каскадных отказов)
   * Если `osago-aggregator` недоступен, `core-app` не отправляет новые запросы и отвечает `503`.
   * Если `osago-aggregator` испытывает проблемы с отдельной страховой, временно перестаёт опрашивать её.
   * **Отразить на схеме возле `core-app → osago-aggregator`**.
3. **Retry** (повтор запросов)
   * Если страховая компания временно недоступна, `osago-aggregator`**повторяет** запрос.
   * Если `osago-aggregator` недоступен, `core-app` делает **несколько попыток** через gRPC.
   * **Отразить на схеме возле `osago-aggregator → страховые компании`**.
4. **Timeout** (таймаут на ожидание ответа)
   * Если страховая не отвечает за 60 сек, `osago-aggregator`**помечает её ответ как "истек таймаут"**.
   * Если `core-app` не получает ответа от `osago-aggregator` за 10 сек, он **возвращает пользователю промежуточные данные**.
   * **Отразить на схеме возле `osago-aggregator → страховые компании` и `core-app → osago-aggregator`**

* **Kafka/Redis распределяет обработку заявок между репликами**.

**Вывод**:
