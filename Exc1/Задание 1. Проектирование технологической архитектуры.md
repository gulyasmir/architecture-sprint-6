**Обновлённая технологическая архитектура InsureTech – To-Be**

## **1. Общий подход**

InsureTech расширяется в регионы РФ, что требует масштабируемой, отказоустойчивой и производительной архитектуры. Основные требования:

* **Высокая доступность** (99.9% uptime)
* **Отказоустойчивость** (RTO ≤ 45 мин, RPO ≤ 15 мин)
* **Географически распределённые пользователи** (минимальные задержки вне зависимости от региона)
* **Готовность к росту нагрузки** (пиковые RPS могут многократно возрасти)

## **2. Масштабирование и отказоустойчивость**

Переходим от **моно-кластера Kubernetes** к **много-зонной геораспределённой архитектуре**.

### **2.1. Kubernetes-кластеры**

* **Мультизонный деплой**: 3+ зоны доступности (МСК, СПб, Сибирь)
* **Подход**:
  * **Один растянутый кластер Kubernetes** между зонами доступности (приоритет)
  * Альтернативно: **независимые кластеры** с сервис-мешем и кросс-зоновой синхронизацией
  * **Ingress-контроллеры (NGINX / Traefik) в каждой зоне** для приёма локального трафика
  * **Horizontal Pod Autoscaler (HPA) + Cluster Autoscaler (CA)**

### **2.2. Балансировка нагрузки**

* **Внешний балансировщик**:
  * **Глобальный Load Balancer (Yandex ALB, AWS ALB, Cloudflare)**
  * Трафик направляется в **ближайший дата-центр** (latency-based routing)
  * **Health-checks в каждой зоне** для мониторинга доступности
* **Внутренний балансировщик** (внутри Kubernetes):
  * **Service Mesh (Istio, Linkerd)** для управления межсервисным трафиком
  * **Canary деплой + Circuit Breaker** для защиты от перегрузок

## **3. Фейловер-стратегия**

* При сбое одной зоны доступности (DC-1 → DC-2):
  * Трафик автоматически переводится в работающий дата-центр
  * PostgreSQL переключается на **реплику в другой зоне**
  * Перезапускаются сервисы в оставшихся дата-центрах через **Kubernetes Cluster Autoscaler**
  * Мониторинг и алерты через **Prometheus + Grafana + Alertmanager**

## **4. Конфигурация базы данных**

Требования: **RTO ≤ 45 мин, RPO ≤ 15 мин**
Текущее состояние: **Один экземпляр PostgreSQL (single master)** → **Недостаточно для отказоустойчивости**

**Будущее решение:**

* **Мастер-репликация PostgreSQL**:
  * **3+ узла PostgreSQL в разных зонах**
  * **Синхронная репликация в пределах зоны**, **асинхронная между зонами**
  * Используем **Patroni / Stolon / Yandex Managed PostgreSQL** для автоматического фейловера
* **Резервное копирование**:
  * WAL-архивирование и **Point-in-Time Recovery (PITR)**
  * **Backup-снимки каждые 5 минут** с хранением в Object Storage
* **Шардирование**:
  * **Citus / YDB / CockroachDB** (горизонтальное масштабирование)
  * Данные клиентов шардируются **по регионам** для минимизации задержек

## **5. Оптимизация производительности**

### **5.1. Кэширование данных**

* **Redis / Memcached** для кэширования запросов API
* Динамические данные (страховые тарифы, расчёты) – **5–15 мин**
* Статические данные (страницы, документы) – **до нескольких часов**

### **5.2. CDN (Content Delivery Network)**

* **Yandex CDN / Cloudflare / Akamai**
* Раздача **статического контента и API** через CDN вблизи пользователей

### **5.3. Асинхронная обработка запросов**

* **Kafka / RabbitMQ / NATS** для асинхронной обработки
* Использование **event-driven архитектуры** для расчётов, платежей, логов

## **6. Безопасность и мониторинг**

### **6.1. DDoS-защита**

* **WAF (Web Application Firewall)**
* **Rate Limiting + API Gateway**
* **DDoS Protection через Yandex / Cloudflare / AWS Shield**

### **6.2. Мониторинг и логирование**

* **Prometheus + Grafana** → мониторинг метрик
* **ELK Stack (Elasticsearch, Logstash, Kibana) / Loki** → сбор логов
* **Alertmanager** → автоматические алерты в Slack / Telegram

## **7. Итоговая схема архитектуры**

1. **Мультизонные Kubernetes-кластеры**
2. **Глобальная балансировка через GLB (географическая маршрутизация)**
3. **PostgreSQL с репликацией + шардированием**
4. **CDN + Redis** для ускорения доступа к данным
5. **Kafka + Event-driven архитектура**
6. **Service Mesh (Istio)** для надежного взаимодействия сервисов
7. **Мониторинг (Prometheus, Grafana, ELK) + автофейловер**

### **Результаты внедрения**

✅ **Устойчивость к сбоям** – выход из строя одной зоны не останавливает работу
✅ **Географическая масштабируемость** – минимизация задержек во всех регионах
✅ **Балансировка нагрузки** – автоматическая маршрутизация в рабочий дата-центр
✅ **Соответствие SLA** – 99.9% доступности, RTO ≤ 45 мин, RPO ≤ 15 мин
✅ **Готовность к росту** – поддержка десятков тысяч пользователей и 1000+ RPS
