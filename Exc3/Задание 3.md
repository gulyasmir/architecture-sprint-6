# Задание 3

Изменения на диаграмме обозначены красным.

Проблемы и риски текущей архитектуры**

* **Высокая нагрузка на core-app**: Монолитное приложение перегружено из-за синхронных запросов и недостатка горизонтального масштабирования.
* **Задержки при работе с ins-product-aggregator**: Получение данных в режиме реального времени создает задержки, особенно при росте числа страховых компаний.
* **Ограниченная отказоустойчивость БД**: Единственный экземпляр PostgreSQL без репликации создает риск отказа всей системы.
* **Низкая масштабируемость API для партнеров**: Один партнер может "съедать" все ресурсы API.
* **Отсутствие мониторинга и алертинга**: Компания узнает о проблемах от пользователей.

### **Изменения, которые нужно внести в диаграмму:**

#### **1. Использование Event-Driven Architecture (EDA)**

* Взаимодействие между **core-app** и **ins-product-aggregator** перевести с REST на асинхронные события (например, Kafka или RabbitMQ).
* Вместо того, чтобы при каждом запросе агрегировать данные от всех страховых компаний, **ins-product-aggregator** должен публиковать обновления продуктов в Event-Streaming-шину.
* **core-app** и **ins-comp-settlement** должны подписываться на эти обновления и сохранять актуальную информацию локально.

#### **2. Внедрение Transactional Outbox**

* Для надежной передачи данных между сервисами использовать паттерн **Transactional Outbox**, чтобы избежать потери сообщений при сбоях.
* **ins-comp-settlement** должен получать данные о страховках не через REST-запросы в core-app, а через события в брокере сообщений.

#### **3. Горизонтальное масштабирование**

* **core-app** и API для партнеров должны быть масштабируемыми. Kubernetes HPA (Horizontal Pod Autoscaler) должен автоматически увеличивать количество реплик в зависимости от нагрузки.
* Ввести **rate-limiting** для партнеров через API Gateway (например, Kong или NGINX Ingress Controller).

#### **4. Оптимизация работы базы данных**

* Внедрить **репликацию PostgreSQL** (Primary-Replica) для увеличения отказоустойчивости.
* Для API-запросов использовать **кеширование** (например, Redis), чтобы снизить нагрузку на основную БД.

#### **5. Улучшение мониторинга и алертинга**

* Включить **Prometheus + Grafana** для мониторинга нагрузки.
* Внедрить **Alertmanager** для уведомлений о сбоях в работе API.
